# TXT 全文搜索（纯 HTML + JS，可直接部署 GitHub Pages）

在 `娱乐/`（含全部子目录）里按关键词搜 TXT 正文，点结果在新窗口打开原文并定位到那一行。
**没有任何后端、没有 Python、没有构建依赖** —— 整个网站就是几个 `.html` / `.js` 文件加一堆 `.txt`。

```
HTML/
├── index.html       搜索页（首页）
├── reader.html      阅读页（带行号，新窗口打开）
├── builder.html     生成文件清单的工具页（可选，加书后重跑一次）
├── manifest.js      文件清单（由 builder.html 生成）
├── .nojekyll        让 GitHub Pages 跳过 Jekyll（必须有，否则 600MB 的 TXT 会被 Jekyll 处理）
├── js/
│   ├── core-util.js     流式解码 + 逐行搜索（Worker 与主线程共用；含快速跳过）
│   ├── idb.js           本机缓存（IndexedDB），搜索/阅读/Worker 共用
│   ├── search-worker.js Web Worker：缓存优先、边下边搜、读完写回缓存
│   ├── common.js        存储配额、取文件、高亮、防误触点击
│   ├── app.js           搜索页逻辑（进度、MB/s、剩余时间）
│   ├── reader.js        阅读页逻辑
│   └── style.css        样式
└── 娱乐/…            原始 TXT，原样上传，不需要任何转换
```

## 部署到 GitHub Pages

1. 把整个 `HTML` 目录的内容 push 到仓库（`娱乐/` 里的 TXT 一起）。
2. 仓库 **Settings → Pages**，Source 选 `Deploy from a branch`，选分支和目录（`/` 或 `/docs`）。
3. 等一分钟，打开 `https://<用户名>.github.io/<仓库名>/`。

> `.nojekyll` 已经放在根目录了，**不要删**：没有它 Pages 会用 Jekyll 处理整个站点，
> 600+ MB 的 TXT 会让构建极慢甚至失败。

## 加书 / 删书之后

打开 `builder.html`，选择一次 `娱乐` 文件夹，点「生成并下载 manifest.js」，
把下载到的 `manifest.js` 覆盖到网站根目录，再 push。**只读文件名和大小，不读内容、不上传任何数据。**

## 不想用服务器？直接双击也行

双击 `index.html` 打开后，点 **「搜索本机文件夹（不上传）」**，选择 `娱乐` 文件夹，
就在本机直接搜索，完全不联网、不需要任何服务器。
（这种方式下浏览器不给用 Worker，会自动退回单线程，速度略慢但功能一样。）

## 关于速度：第一次搜索要下载语料

纯静态方案没有服务器可以替你搜，浏览器只能**把 TXT 下载下来在本地搜**。
这是唯一可行的做法（我实测过：想预先把关键词索引做小是不可能的，本语料有 224 万个不同的
二字组合、2500 万条索引记录，索引本身就要 47~60 MB，比直接下载还亏）。

### 慢在哪里（实测数据，不是猜的）

| 环节 | 实测 |
| --- | --- |
| 扫描 641 MB 全部正文（CPU） | **约 2 秒**（单线程；8 个 Worker 分摊后不到 1 秒） |
| 从 Pages 下载（边缘缓存**命中**） | **2.6 MB/s** |
| 从 Pages 下载（边缘缓存**未命中**，回源） | **约 36 KB/s**（慢 72 倍） |

所以瓶颈从来不是「扫描算法」，而是**要下多少字节**，以及**是不是每次都在重新下载**。
针对这两点做了四件事：

1. **搜索走本机缓存**（原来只有阅读页用缓存，搜索每次都把 641 MB 重下一遍——这才是卡的真凶）。
   下载过的书存进 IndexedDB，第二次搜索 **0 字节下载**。
2. **多开并行连接**：边缘未命中时单条连接只有几十 KB/s，多连接才吃得满带宽（默认 4–8 条）。
3. **扫描快 1.7–3.2 倍**：整块没有关键词时不再切行、不再逐行匹配。
   另外中文关键词下「忽略大小写」是空操作，不再因此走慢路径。
   （逻辑与旧实现逐字节对拍，结果完全一致。）
4. **状态栏显示 MB/s 和剩余时间**，慢也慢得看得见。

### 实际体验

| 场景 | 实际开销 |
| --- | --- |
| 常见词（默认每本 200 行上限） | 够数就中断下载，全部 189 本只读 46 KB |
| 冷僻词，**第一次**搜全库 | 要下完整个范围：641 MB。边缘缓存未命中时非常慢，命中后约 4 分钟 |
| **第二次**搜同一个范围 | **0 字节下载**，纯本地扫描，**几秒** |
| 点搜索结果打开原文 | 搜索时已经把整本缓存了，**打开是瞬时的**，不再重新下载 |

> 结论：**第一次搜索是唯一一次付出下载代价**。可以用下面两个办法让代价变小：
> **范围选择器**（只搜某个子目录，下载量立刻降到几十 MB），
> 或者点 **「缓存整个书库」** 一次性把 189 本存到本机——之后所有搜索都不再联网。

本机缓存上限会按浏览器给的配额自动定（默认目标：放得下整个语料，最多 1.5 GB，
且不超过可用空间的 60%）。可在页面上开关或一键清空。


## 页面功能

**搜索页**

- 结果按 **每本的命中条数从多到少** 排列，每条显示「N 行」；`200+ 行` 表示达到上限提前停止。
- 每本默认折叠，点标题展开；展开时才生成行内容，即使几千条结果也不卡。
- 每行都标出 **在原文中的行号**，并高亮关键词，显示该行完整文字。
- 支持 **忽略英文大小写** 与 **正则**（如 `第[0-9]+章`）。
- **缓存整个书库** 按钮：一次把 189 本下载到本机（有进度、可取消），之后搜索完全离线。
- 状态栏实时显示已扫描本数、命中条数、**下载速度 MB/s 与剩余时间**。
- **防误触**：必须是「按下与抬起几乎在同一点、且 700 毫秒内」的干净轻点才会跳转；
  滑动、拖动、长按选字都不会误开新窗口。桌面端另有「打开原文 ↗」按钮。
- 搜索中可随时「取消」。

**阅读页**

- 左侧固定行号栏，右上角实时显示「第 N 行 / 共 M 行」。
- 顶部可输行号跳转；`↑ 上一处 / ↓ 下一处` 在关键词命中行之间移动。
- `A- / A+` 调字号（会记住）；快捷键 `n`/`p` 或 `]`/`[` 切换命中，`/` 聚焦跳转框。
- 目标行高亮并闪一下，方便在手机上找。
- **大文件不会整篇塞进页面**：只保留视口附近约 10 个分块（约 1500 行），
  其余随时回收，所以 67 万行的文件和 1 千行的文件一样好滑（实测第 1 屏约 1 秒）。

## 编码

自动识别，UTF-8 优先，失败按 GB18030 处理（本机语料实测 **178 个 UTF-8 + 11 个 GB18030**，两类都能正常搜和读）。
探测时会特意处理「采样切片正好切断一个汉字」的情况——否则 100 多个 UTF-8 文件会被误判成 GBK。

## GitHub 的几个硬限制

- 单个文件超过 **100 MB** 会被拒绝，超过 **50 MB** 会警告。本语料最大 31 MB，安全。
- 发布出来的站点上限 **1 GB**。本语料 641 MB，接近但没超；`builder.html` 会在超限时提醒你。
- 流量软上限 100 GB/月：每次冷启动全库搜索约 200–250 MB，够搜几百次。

## 本机预览（可选）

要看部署后的效果，需要任意静态服务器（`file://` 下浏览器禁止 `fetch` 本地文件）。
随便哪种都行，例如 VS Code 的 Live Server 插件，或在这台机器上：

```bat
python -m http.server 8080
```

然后打开 <http://127.0.0.1:8080/>。**只有预览才需要这样做，GitHub Pages 上什么都不用。**
